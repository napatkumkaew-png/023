## 2. 🛡️ มาตรฐานความปลอดภัยที่ระบบยึดถือ (Security Principles)

ระบบถูกออกแบบตามแนวทาง **OWASP ASVS** และ **NIST SP 800-63B (Digital Identity Guidelines)** โดยมีข้อกำหนดสำคัญดังนี้:

1. **ความยาวรหัสผ่าน (Password Length):**
   - **ขั้นต่ำ 15 ตัวอักษร:** เพื่อต้านทานการโจมตีแบบ Brute-force และรองรับการใช้ **Passphrase** (วลีที่มีความหมายและยาว)
   - **เพดานสูงสุด 128 ตัวอักษร:** รองรับรหัสผ่านยาวมากกว่า 64 ตัวอักษรขึ้นไปได้อย่างสมบูรณ์ และจำกัดไว้ที่ไม่เกิน 128 ตัวอักษร เพื่อป้องกันการโจมตีแบบ **Denial of Service (DoS)** ต่อกระบวนการคำนวณ Password Hashing (เช่น Argon2, bcrypt, PBKDF2)
2. **การนับตัวอักษรแบบ Unicode Code Points จริง:**
   - ให้นับตามตัวอักษรจริง 1 ตัวอักษร = 1 Code Point ไม่ใช่นับตามจำนวน Byte หรือหน่วยเก็บในหน่วยความจำ (UTF-16 Code Units)
   - รองรับตัวอักษรภาษาไทย, อักขระพิเศษ, ช่องว่าง (Space), และ Emoji
3. **ไม่บังคับความซับซ้อนของตัวอักษร (No Composition Rules):**
   - ไม่บังคับว่าต้องมีตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก ตัวเลข หรือสัญลักษณ์พิเศษ เนื่องจากงานวิจัยของ NIST พบว่าการบังคับกฎเหล่านี้มักทำให้ผู้ใช้ตั้งรหัสผ่านตามรูปแบบที่คาดเดาได้ง่าย (เช่น `P@ssw0rd1!`)
4. **อนุญาตช่องว่าง และ "ห้าม" ใช้ `.trim()` / `.strip()` บนรหัสผ่าน:**
   - ผู้ใช้มีสิทธิ์ตั้งรหัสผ่านที่มีช่องว่างนำหน้า ตรงกลาง หรือต่อท้าย (เช่น `"  my secret long passphrase  "`) การตัดช่องว่างหัวท้ายจะทำให้ Entropy ของรหัสผ่านลดลง
   - โปรแกรมจะตัดเฉพาะอักขระขึ้นบรรทัดใหม่ (`\r`, `\n`) ที่เกิดจากการกดแป้นพิมพ์ Enter เท่านั้น
5. **ความปลอดภัยในการป้อนข้อมูล (Input Privacy & Sanitization):**
   - **ไม่แสดงรหัสผ่านซ้ำบนหน้าจอ** หลังจากการกรอกเสร็จสิ้น (ป้องกัน Shoulder Surfing)
   - **ไม่มีการบันทึก (Logging)** รหัสผ่านลงในไฟล์หรือคอนโซล
   - จำกัดจำนวนครั้งในการกรอกผิดได้ไม่เกิน **3 ครั้ง** หากเกินจะตัดการทำงานทันที

## 3. 🔍 ตารางเปรียบเทียบการทำงานในแต่ละภาษา

| หัวข้อ | JavaScript (Node.js) | Python 3 | Rust |

## 5. 🔍 วิธีการติดตั้งและสแกนความปลอดภัยด้วย Semgrep

[Semgrep](https://semgrep.dev/) เป็นเครื่องมือ Static Application Security Testing (SAST) ประสิทธิภาพสูง ใช้ตรวจจับช่องโหว่ความปลอดภัย โค้ดที่ไม่ปลอดภัย และข้อผิดพลาดตามมาตรฐาน OWASP

### 📦 วิธีการติดตั้ง Semgrep:

- **ผ่าน Python pip (แนะนำสำหรับ Windows, macOS, Linux):**
  ```powershell
  pip install semgrep
  ```
- **ผ่าน Homebrew (macOS):**
  ```bash
  brew install semgrep
  ```
- **ตรวจสอบการติดตั้ง:**
  ```powershell
  semgrep --version
  ```

---

### 🛡️ วิธีการสั่งรันสแกน Semgrep:

1. **สแกนแบบอัตโนมัติทั้งโปรเจกต์ (Default Auto Config):**
   ```powershell
   semgrep scan --config auto
   ```
2. **สแกนเจาะจงตามกฎ OWASP Top 10:**
   ```powershell
   semgrep scan --config "p/owasp-top-ten"
   ```
3. **สแกนเจาะลึกด้านความปลอดภัย (Security Audit):**
   ```powershell
   semgrep scan --config "p/security-audit"
   ```
4. **สแกนเฉพาะไฟล์ที่ต้องการ (เช่น JavaScript):**
   ```powershell
   semgrep scan --config auto main_checker.js
   ```

### 💡 คำอธิบายผลลัพธ์ (Analysis & Findings Explanation):

1. **ผลการสแกนเป็น 0 Findings (ผ่านเกณฑ์ความปลอดภัย 100%):**
   - **No Hardcoded Secrets:** ไม่มีการฮาร์ดโค้ด Credential, API Key, หรือรหัสผ่านลงในโค้ดต้นฉบับ
   - **No Injection Vulnerabilities:** ไม่มีการใช้ฟังก์ชันเสี่ยงต่อ Injection เช่น `eval()`, `exec()`, หรือการเชื่อมต่อ String เพื่อส่งเข้า Command Shell โดยตรง
   - **Memory & Logging Safety:** รหัสผ่านที่รับเข้ามาถูกประมวลผลในหน่วยความจำชั่วคราวเท่านั้น ไม่มีการเขียนบันทึก (Logging) ลงในไฟล์ Log หรือแสดงผลค่ารหัสผ่านซ้ำออกมาที่หน้าจอคอนโซล
   - **DoS Prevention:** มีการกำหนดความยาวเพดานสูงสุดของรหัสผ่าน (128 ตัวอักษร) ช่วยป้องกัน CPU Exhaustion DoS ต่อฟังก์ชัน Hash
2. **ข้อสังเกตและข้อจำกัดของ SAST:**
   - เครื่องมือ SAST เช่น Semgrep ทำหน้าที่ตรวจจับ Pattern ของโค้ดที่ไม่ปลอดภัย (Source & Sink) แต่ไม่สามารถตรวจสอบความถูกต้องของ **Business Logic** เช่น *การนับจำนวนอักขระ Unicode ด้วย Code Point หรือการห้ามใช้ `.trim()`* ดังนั้น กลุ่มผู้พัฒนาจึงต้องทำการ **Manual Code Review** และเขียนชุดการทดสอบ (Test Cases) ควบคู่ไปด้วยเสมอ

## 7. 🧪 ตารางกรณีทดสอบ ผลลัพธ์ที่คาดหวัง และผลลัพธ์จริง (Test Cases)

การทดสอบดำเนินการครอบคลุมทั้งกรณี Username (Email) และ Password ตามมาตรฐาน OWASP / NIST SP 800-63B:

| ลำดับ | กรณีทดสอบ (Scenario) | ข้อมูลนำเข้า (Input) | ผลลัพธ์ที่คาดหวัง (Expected Result) | ผลลัพธ์จริง (Actual Result) | สถานะ |
| :---: | :--- | :--- | :--- | :--- | :---: |
| **TC-01** | Email ไม่มีเครื่องหมาย `@` | `usernameexample.com` | ❌ ไม่ผ่าน: รูปแบบอีเมลไม่ถูกต้อง และแจ้งโอกาสที่เหลือ | ❌ ผลลัพธ์: ไม่ผ่าน (รูปแบบอีเมลไม่ถูกต้อง) | **PASS** |
| **TC-02** | Email ไม่มี Domain/TLD | `admin@` หรือ `user@domain` | ❌ ไม่ผ่าน: รูปแบบอีเมลไม่ถูกต้อง | ❌ ผลลัพธ์: ไม่ผ่าน (รูปแบบอีเมลไม่ถูกต้อง) | **PASS** |
| **TC-03** | Email ถูกต้องตามมาตรฐาน | `user.test@mycompany.co.th` | ✅ ผ่าน: ยอมรับ Username และไปขั้นตอนกรอกรหัสผ่าน | ✅ ผ่าน: เข้าสู่การถามรหัสผ่าน | **PASS** |
| **TC-04** | รหัสผ่านสั้นเกินไป (< 15 ตัวอักษร) | `Admin@12345` (11 ตัว) | ❌ ไม่ผ่าน: แจ้งว่าต้องมีอย่างน้อย 15 ตัวอักษร | ❌ ไม่ผ่าน: ต้องมีอย่างน้อย 15 ตัวอักษร (ปัจจุบันมี 11) | **PASS** |
| **TC-05** | รหัสผ่านยาว 15 ตัวอักษรพอดี (Boundary) | `15CharactersOK!` (15 ตัว) | ✅ ผ่าน: ผ่านเกณฑ์ความยาวขั้นต่ำ | ✅ ผ่าน: รหัสผ่านผ่านเกณฑ์ความปลอดภัย OWASP | **PASS** |
| **TC-06** | รหัสผ่านแบบ Passphrase มีช่องว่างหัวท้าย | `   my long secure pass   ` | ✅ ผ่าน: ห้ามตัด Space (นับรวมได้ 25 ตัว) | ✅ ผ่าน: ช่องว่างไม่ถูกตัดออก และนับความยาวถูกต้อง | **PASS** |
| **TC-07** | รหัสผ่านเป็นภาษาไทย (Unicode) | `รหัสผ่านปลอดภัยมากครับ` (20 ตัว) | ✅ ผ่าน: นับตัวอักษรไทยเป็นตัวอักษรจริง | ✅ ผ่าน: นับได้ 20 ตัวอักษร และผ่านเกณฑ์ | **PASS** |
| **TC-08** | รหัสผ่านผสม Emoji หลากชนิด | `PassKey🔒🔑🛡️Safe!` (18 ตัว) | ✅ ผ่าน: นับ Emoji 1 รูป = 1 Code Point | ✅ ผ่าน: นับ Emoji ได้ถูกต้อง (ไม่นับเป็น 2 byte/unit) | **PASS** |
| **TC-09** | รหัสผ่านยาวมาก 64 ตัวอักษรขึ้นไป | ข้อความ 70 ตัวอักษร | ✅ ผ่าน: รองรับรหัสผ่านยาวตามเกณฑ์ 64+ | ✅ ผ่าน: รองรับได้โดยไม่มีการตัดทอนรหัสผ่าน | **PASS** |
| **TC-10** | รหัสผ่านยาวเกินเพดาน DoS (> 128 ตัว) | ข้อความ 135 ตัวอักษร | ❌ ไม่ผ่าน: ปฏิเสธเพื่อป้องกัน DoS Attack | ❌ ไม่ผ่าน: แจ้งว่ายาวเกิน 128 ตัวอักษรเพื่อความปลอดภัย | **PASS** |
| **TC-11** | กรอกข้อมูลผิดติดต่อกัน 3 ครั้ง | ป้อนข้อมูลผิด 3 ครั้งต่อเนื่อง | ❌ ระบบแจ้งเตือนครบ 3 ครั้ง และเด้งออกจากระบบ | ❌ แจ้ง "ใส่ข้อมูลผิดเกิน 3 ครั้ง เด้งออกจากระบบ!" และหยุดทำงาน | **PASS** |
| **TC-12** | ความปลอดภัยของหน้าจอ (Privacy) | ขณะพิมพ์รหัสผ่าน | 🔒 หน้าจอแสดงเป็น `*` หรือไม่แสดงตัวอักษร | 🔒 รหัสผ่านถูก Mask ด้วย `*` ไม่มีการ echo ตัวจริง | **PASS** |

### 💬 Prompt ที่กลุ่มใช้สั่งงาน AI:

#### Prompt 1 (Prompt เริ่มต้น: การแปลงและปรับปรุงโค้ดตามเกณฑ์ความปลอดภัย OWASP):
```text
ช่วยแปลงและปรับปรุงโค้ดตรวจสอบรหัสผ่านภาษา Python ด้านล่างนี้ ให้เป็นโปรแกรมใหม่ 2 ภาษา ได้แก่:
1. JavaScript (ทำงานบน Node.js)
2. Rust

โดยโปรแกรมทั้งสองเวอร์ชันต้องทำงานตามข้อกำหนด (อิงตามแนวทาง OWASP) ดังนี้:
1. รับค่า username (รูปแบบ email) และ password จากผู้ใช้ผ่านทางหน้าจอ (CLI)
2. ตรวจสอบความยาวรหัสผ่าน: ต้องมีความยาวตั้งแต่ 15 ตัวอักษรขึ้นไป (นับตามจำนวนตัวอักษรจริง/Unicode character ไม่ใช่นับตามจำนวน byte)
3. ไม่บังคับความซับซ้อนของชุดอักขระ (ไม่ต้องบังคับให้มีตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก ตัวเลข หรือสัญลักษณ์พิเศษ)
4. อนุญาตให้ใช้ช่องว่าง (Space) และอักขระ Unicode (เช่น ภาษาไทย หรือ Emoji) ได้ และ "ห้าม" ใช้คำสั่งตัดช่องว่างหัวท้าย (เช่น .trim()) ออกจากรหัสผ่านก่อนนำไปตรวจสอบเด็ดขาด
5. รองรับรหัสผ่านที่มีความยาวอย่างน้อย 64 ตัวอักษร (และยาวกว่านั้นได้) โดยห้ามตัดทอนรหัสผ่านให้สั้นลงโดยไม่แจ้งผู้ใช้
6. แสดงผลลัพธ์ว่ารหัสผ่าน "ผ่าน" หรือ "ไม่ผ่าน" พร้อมระบุเหตุผลที่ชัดเจน แต่ "ห้าม" แสดงค่ารหัสผ่านที่ผู้ใช้กรอกออกมาซ้ำบนหน้าจอ และ "ห้าม" บันทึกรหัสผ่านลงไฟล์ใดๆ ทั้งสิ้น

สิ่งที่ต้องการให้ตอบ:
- โค้ดฉบับสมบูรณ์ของทั้ง JavaScript (Node.js) และ Rust ที่สามารถรันใช้งานได้ทันที (พร้อมระบุวิธีรันคร่าวๆ)
- อธิบายการทำงานของส่วนที่จัดการเรื่องความยาว Unicode และการไม่ตัดช่องว่างหัวท้ายในแต่ละภาษา
```

### 🛠️ ตัวอย่างจุดสำคัญที่กลุ่มตรวจสอบและแก้ไขจากโค้ดของ AI (Human-in-the-Loop Review):

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       จุดที่กลุ่มตรวจสอบและปรับปรุงแก้ไขโค้ดจาก AI                     │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### จุดที่ 1: การนับความยาวตัวอักษร Unicode ใน JavaScript (UTF-16 vs Code Points)
- **โค้ดที่ AI สร้างตอนแรก:**
  ```javascript
  // โค้ดเริ่มต้นที่ AI สร้าง
  if (password.length < 15) { ... }
  ```
- **ปัญหาที่กลุ่มตรวจพบ:**
  ใน JavaScript พร็อพเพอร์ตี้ `.length` จะนับตาม **UTF-16 Code Units (16-bit)** เมื่อผู้ใช้ใส่อักขระที่มีขนาดมากกว่า 16-bit เช่น Emoji (`🔒`, `😀`) หรืออักษรเสริม JavaScript จะมองเป็น **Surrogate Pair (นับเป็น 2)** ทำให้ผู้ใช้กรอกรหัสผ่านเพียง 10 ตัวที่มี Emoji ผสมอยู่ แต่โปรแกรมนับเกินจริงและอาจให้ผ่านแบบผิดสเปก
- **การแก้ไขของกลุ่ม:**
  กลุ่มได้แก้ไขโดยใช้ `Array.from()` หรือ Spread Operator `[...password]` ซึ่งตัว String Iterator ของ ES6 จะแตกตาม **Unicode Code Points** จริง:
  ```javascript
  // โค้ดที่กลุ่มแก้ไขให้ถูกต้องตาม NIST SP 800-63B
  const charCount = Array.from(password).length;
  if (charCount < 15) { ... }
  ```

---

#### จุดที่ 2: ปัญหา AI เผลอใส่ `.trim()` กับรหัสผ่าน
- **โค้ดที่ AI สร้างตอนแรก:**
  ```javascript
  // AI มักเผลอใช้ trim() กับ input ทุกตัว
  const password = rawPassword.trim();
  ```
- **ปัญหาที่กลุ่มตรวจพบ:**
  AI มักมีความเคยชินที่จะใส่ `.trim()` เพื่อล้างข้อมูลอินพุต แต่การทำเช่นนั้นจะตัด Space หน้าและหลังที่ผู้ใช้ตั้งใจตั้งเป็นส่วนหนึ่งของ Passphrase (เช่น `"  passphrase  "`) ซึ่งขัดต่อข้อกำหนด OWASP
- **การแก้ไขของกลุ่ม:**
  กลุ่มได้แยกฟังก์ชันสำหรับตัดเฉพาะตัวขึ้นบรรทัดใหม่ (`\r\n` และ `\n`) ที่เกิดจากการกดแป้นพิมพ์ Enter ออก โดยรักษาช่องว่างทุกตำแหน่งไว้อย่างสมบูรณ์:
  ```javascript
  // โค้ดที่กลุ่มเขียนควบคุมเฉพาะ Line Ending
  function stripLineEnding(str) {
      if (str.endsWith('\r\n')) return str.slice(0, -2);
      if (str.endsWith('\n') || str.endsWith('\r')) return str.slice(0, -1);
      return str;
  }
  ```

#### จุดที่ 3: การรั่วไหลของรหัสผ่านบนหน้าจอ (Password Exposure)
- **โค้ดเดิม / จุดเสี่ยง:**
  โค้ดโปรแกรมตั้งต้นใน Python มีคำสั่ง:
  ```python
  print("รหัสของคุณคือ:", password)  # อันตราย: แสดงรหัสผ่านเป็น Plaintext บนหน้าจอ
  ```
- **การแก้ไขของกลุ่ม:**
  กลุ่มได้ลบคำสั่งแสดงค่ารหัสผ่านดังกล่าวออกทั้งหมด และในเวอร์ชัน JavaScript ได้เขียนระบบรับอินพุตผ่าน `process.stdin.setRawMode(true)` เพื่อ Mask ตัวอักษรที่พิมพ์เป็นเครื่องหมายดอกจัน `*` แบบเรียลไทม์ ป้องกันการมองข้ามไหล่ (Shoulder Surfing) อย่างสมบูรณ์

#### จุดที่ 4: การกำหนดเพดานความยาวสูงสุดเพื่อป้องกัน Denial of Service (DoS)
- **ปัญหาที่กลุ่มตรวจพบ:**
  เมื่อโจทย์ระบุว่า *"ต้องรองรับรหัสผ่าน 64 ตัวอักษรขึ้นไปได้โดยไม่ตัดทอน"* AI บางตัวเขียนโค้ดที่ไม่มีการกำหนดเพดานบนเลย ซึ่งเปิดช่องโหว่ให้ผู้ไม่หวังดีส่งรหัสผ่านยาวหลายแสนตัวอักษรเข้ามา ทำให้เซิร์ฟเวอร์เกิดปัญหา CPU Exhaustion DoS ในกระบวนการคำนวณ Hashing (เช่น Argon2 หรือ bcrypt)
- **การแก้ไขของกลุ่ม:**
  กลุ่มได้เพิ่มเงื่อนไขเพดานสูงสุดที่ **128 ตัวอักษร** ตามคำแนะนำของ NIST SP 800-63B Section 5.1.1.2 เพื่อความปลอดภัยสูงสุด:
  ```javascript
  if (charCount > 128) {
      return {
          isValid: false,
          reason: `รหัสผ่านยาวเกินไป: อนุญาตไม่เกิน 128 ตัวอักษรเพื่อความปลอดภัยของระบบ (ปัจจุบันมี ${charCount} ตัวอักษร)`
      };
  }
  ```
